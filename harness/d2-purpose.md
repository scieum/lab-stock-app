# 개발 하네스 목적 (D2)

> 디자인 정답지: `DESIGN-HARNESS` 저장소 (github.com/scieum/harness, 기준 커밋 129ccb6)
> 이 저장소는 그 시안·규칙을 **코드로 옮기고, 같은 규칙을 코드에서 기계로 검사**한다.

## 1. 스택 (2026-10-02 결정)

| 영역 | 선택 | 이유 |
|---|---|---|
| 앱 | Next.js (App Router) + TypeScript | 서버 코드(Route Handler)로 키를 숨기기 쉬움 → N2 |
| DB·로그인·권한 | Supabase (Postgres + Auth + RLS) | 행 수준 보안으로 학교별 분리를 DB에서 강제 → N1 |
| 배포 | Vercel | PR마다 미리보기 URL → 사람 승인에 사용 |
| 스타일 | CSS 변수(디자인 토큰) + CSS Modules | 토큰 밖 값 검사(T2)가 쉬움 |
| 테스트 | Vitest(단위) · Playwright(화면·역할·스크린샷) · SQL 테스트(RLS) | |

## 2. MVP 범위 (1차)

| 화면 | 이름 | 이유 |
|---|---|---|
| 1 | 로그인·학교 선택 (NEIS 시/도 → 지역 → 학교) | 모든 흐름의 시작, N1·N2 첫 적용 |
| 13 | 홈 | 앱의 얼굴, 탭바·요약 |
| 2 | 시약 목록 | 핵심 데이터 |
| 3 | 시약 상세 (MSDS) | 모든 역할 필수 진입점 |
| 4 | 사용 기록 입력 | 학생도 쓰는 유일한 쓰기 기능 |

- 공통: 하단 탭바(모바일), 상단 nav-pill(데스크탑), 역할 3종(학생·교사·admin)
- 2차 이후: 7 입고 → 10 기록 내역 → 11 시약장 → 12 QR → 5 매뉴얼(Gemini) → 6·9 판매처 → 8 사용자 관리

## 3. 완료 기준 (한 문장)

MVP 화면 5개가 390·1440 두 폭에서 동작하고, 개발 게이트(D5) 위반 **0건**, 사람 승인 **1건**(미리보기 URL)이 있으면 1차 완료다.

## 4. 어기면 안 되는 것 (디자인 하네스 N1·N2의 코드판)

| # | 코드에서 지키는 방식 | 검사 |
|---|---|---|
| N1 학교별 분리 | 모든 업무 테이블에 `school_id`, RLS = 로그인 사용자의 school_id만 | 다른 학교 사용자로 조회·수정 시 0행 (D5 N1-db) |
| N2 키는 서버에서만 | NEIS·Gemini 키는 `NEIS_API_KEY`·`GEMINI_API_KEY`(NEXT_PUBLIC_ 금지), Route Handler에서만 사용 | 빌드된 브라우저 번들에 키 형식 문자열 0 (D5 N2-bundle) |
